# 02 Questions Round 1 — promote `--icm` to default

Please answer each question below (select one or more options, or add your own notes). Feel free to add additional context under any question.

> **Why this round exists.** The request is one sentence and it *reverses a recorded decision*. ADR-279 explicitly considered and rejected "make `--icm` the default". So this is not a patch — it is a behaviour change that must be accompanied by an ADR that supersedes the old reasoning, and by tests that would otherwise go **silently green while proving nothing**.
>
> **Context found during assessment** (measured against the built CLI, not recalled):
>
> - **Only 2 of 20 templates can emit ICM.** `minimal` and `vertical:coding` are the only template dirs carrying a `.icm/` overlay — and they are exactly the two whose `catalog.json` entry has an `icm` block. The other 18 are no-ops for the flag.
> - **There is no capability gate in the scaffold path.** ICM is decided at two bare flag checks — `src/index.ts:694` (walk) and `:855` (onboarding) — both `opts.icm === true`. `catalog.json`'s `icm.enabled` is read *only* by `validate.ts`, to check an already-emitted tree. Non-capable templates are inert because they have no `.icm/` directory to include, **not** because anything declared them incapable. The gate this spec needs must be *introduced*.
> - **`--no-icm` already exists and is already parsed** (`:227`), and is threaded through. The opt-out needs no new flag.
> - **`--icm` is not a *total* no-op on non-capable templates.** Files are identical, but stdout gains a spurious line: `Onboarding: interactive (0 questions)`. A naive global flip would replicate that across all 18.
> - **`doctor` infers ICM from the manifest's file list**, not the flag (`validate.ts:263-269`), and SKIPs with the string `'not generated with --icm'` — which becomes actively wrong after the flip.
> - **`upgrade` is already safe** — `upgrade-cmd.ts` derives `icmEnabled` from the harness's own manifest, so a flip cannot mis-classify a pre-flip harness.
> - **Two tests would go vacuous.** `icm-off.test.ts` builds its flagless case with `icm: undefined`, which a capability-gated flip resolves to **true** for `vertical:coding` — it would compare an ICM scaffold against itself and still pass. `scaffold-e2e.test.ts`'s byte-equality case scaffolds `vertical:coding` flagless and asserts `stages/` is absent; that must move to `--no-icm`.
> - **Measured delta on the capable template:** flagless 20 files → `--icm` 30 files (+`CONTEXT.md`, `references/CONTEXT.md`, `stages/01-plan`, `02-implement`, `03-test`, `04-review`, each with `CONTEXT.md` + `output/.gitkeep`).

## 1. Scope — which templates default-on?

`minimal` and `vertical:coding` are both genuinely ICM-capable (both have a `.icm/` overlay). Both could flip. But `minimal` is a different proposition from a vertical.

- [ ] (A) **`vertical:coding` only.** The template whose name promises "smallest output" stays ICM-free unless asked.
- [ ] (B) **Both capable templates** — `minimal` and `vertical:coding`.
- [ ] (C) **All 20 templates, adding `.icm/` overlays to the other 18** so the default means something everywhere.
- [ ] (D) Other (describe).

**Recommended answer(s):** [(A)]

**Why:**

- `(A)` respects the template's own name. `minimal` is what a user reaches for when they want *less*; silently giving them a five-layer tree inverts the one thing the template sells. Its catalog entry is also `generate: false` and the vertical tour deliberately excludes it — two existing signals that `minimal` is not meant to be generated by default.
- `(B)` is defensible if your intent is "ICM is the house style, period" — but it changes the meaning of the template named *minimal*, and that is a bigger claim than "promote `--icm` to default" literally asks for.
- `(C)` is a **different spec** (authoring 18 ICM overlays, each with real staged content and a line budget). Folding it in turns a default flip into content authoring and makes the non-goals muddy. If you want this, say so and I'll split it out.

## 2. The resolver's predicate — one conjunct or two?

`minimal` is `icm.enabled: true` **and** `generate: false`.

- [ ] (A) **`icm.enabled` alone.** "Capable ⇒ default-on." Simplest predicate; `minimal` flips too (which forces Q1 = (B)).
- [ ] (B) **`generate !== false && icm.enabled`.** "Capable *and* default-generated here." Encodes Q1(A) as data rather than a special case.
- [ ] (C) **An explicit new field** (e.g. `icm.defaultOn: true`) so capability and defaulting are independently declarable.
- [ ] (D) Other (describe).

**Recommended answer(s):** [(B)]

**Why:**

- `(B)` makes the code read as the policy: a template defaults-on when it is *both* capable and generated in the default flow. It also means Q1 falls out of the catalog instead of needing a hard-coded exception for `minimal` — which is exactly the kind of exception that rots.
- `(A)` is the smallest possible predicate and is right *if* Q1 = (B). It is not wrong, merely less expressive; the cost is that "capable" and "default-on" become the same fact permanently.
- `(C)` is the most explicit and is the right long-term shape if you expect the two to diverge again — but it adds a schema field to solve a problem `generate` already answers. Choose it only if you want the declaration to be unambiguous on its own terms.

## 3. Rollout — clean flip, or a deprecation window?

- [ ] (A) **Clean flip.** Default changes immediately; `--no-icm` is the escape hatch; changelog leads with the behaviour change.
- [ ] (B) **Warn first, flip later.** One or more releases where a flagless capable scaffold warns "ICM will become default in vX"; flip after.
- [ ] (C) **Clean flip + a one-line note** in the scaffold output pointing at `--no-icm`.
- [ ] (D) Other (describe).

**Recommended answer(s):** [(C)]

**Why:**

- `(C)` is `(A)` plus the cheapest possible affordance: the user who is surprised by a new tree has the opt-out *in front of them* at the moment of surprise, rather than in a changelog they may never read. One `console.log` line.
- `(B)` is the conservative choice and is not unreasonable — but the exposed surface is **one template**, and the old behaviour is exactly preserved by a flag that already exists. A warning release with no behaviour change mostly spends calendar time.
- `(A)` is fine if you consider the CLI's contract too young to need the note; `(C)` just costs one line more.

## 4. `doctor`'s SKIP message — reword it, or leave it?

Today an ICM-less harness reports `icm-structure SKIP — not generated with --icm`.

- [ ] (A) **Reword** to name the real causes: pre-flip scaffold, or `--no-icm`.
- [ ] (B) **Leave it** — it only appears on non-ICM harnesses, which is not what this change is about.
- [ ] (C) **Reword and make it louder** — treat "capable template but no `stages/`" as a diagnostic worth surfacing, since post-flip that is *unexpected*.
- [ ] (D) Other (describe).

**Recommended answer(s):** [(A)]

**Why:**

- `(A)` is a one-string change whose absence is actively misleading. After the flip, "not generated with `--icm`" is the *least* likely explanation for a missing tree. The people who read `doctor` output are exactly the people this string would misdirect.
- `(C)` is tempting and may be right, but note the asymmetry: the very same SKIP must stay quiet for the 18 non-capable templates and for legitimately-old harnesses. Making it loud risks a false alarm on the common case. Reword now; escalate only if you want it.
- `(B)` is the "out of scope" answer, and I'd push back gently — this message is a *direct* consequence of the change, not an unrelated wart.

## 5. ADR — supersede ADR-279 in place, or write ADR-280?

ADR-279 recorded "make `--icm` the default" as *considered and rejected*. `INDEX.md` states a ratified ADR is amended by a follow-on ADR, never edited in place.

- [ ] (A) **New ADR-280**, citing 279, recording *what changed in the evidence* that reversed the decision.
- [ ] (B) **Amend ADR-279 in place**, striking the rejected alternative.
- [ ] (C) **New ADR-280 + a pointer line added to 279's alternative** (so a reader of 279 is not misled).
- [ ] (D) Other (describe).

**Recommended answer(s):** [(C)]

**Why:**

- `(C)` satisfies the repo's own rule *and* closes the trap: someone reading ADR-279 alone would still see "rejected" and not know it was reversed. A one-line pointer in 279 ("superseded by ADR-280") costs nothing and prevents that.
- `(A)` is correct by the letter of the rule but leaves 279 self-contradicting the shipped behaviour — the next reader has to discover 280 by luck.
- `(B)` violates `INDEX.md`'s convention and, worse, erases the *reasoning trail*: the fact that this was considered, rejected, and later reversed **on measurement** is the most valuable part of the record. Don't delete it.

## 6. The tests that would go vacuous — how do we guarantee they don't?

- [ ] (A) **Re-point both tests** (`icm-off.test.ts` → explicit `false`; e2e byte-equality → `--no-icm`) in the same change, and add default-on assertions.
- [ ] (B) **`(A)` plus a mutation check** — deliberately flip the resolver back and confirm the re-pointed tests actually fail, proving they still bind.
- [ ] (C) **`(A)` plus a stdout assertion** that non-capable templates never print `Onboarding:`.
- [ ] (D) Other (describe).

**Recommended answer(s):** [(B) + (C)]

**Why:**

- This is the sharp edge of the whole change. `icm-off.test.ts` passes `icm: undefined` for "flagless"; post-flip that means *on* for a capable template, so the test would compare an ICM scaffold to itself and stay **green**. A test that reports green while its invariant is dead is worse than a failing one.
- `(B)` applies the repo's own established practice — the ICM work falsified its new guards by mutation before committing. Same standard here: if the re-pointed test cannot fail when the behaviour is wrong, it isn't a guard.
- `(C)` covers the §3.3 leak: non-capable + `--icm` should be silent as well as file-identical. It is cheap and pins a real regression (the naive global flip breaks it).

## 7. Version, changelog, and the residual-placeholder note

- [ ] (A) **`minor`** bump; changelog leads with the behaviour change; leave the `8 ICM placeholder(s) left for setup` note alone.
- [ ] (B) **`minor`**, and **also** fix the residual count — 3 of the 8 are conditional markers (`?SUBAGENT_HANDOFF`, `/SUBAGENT_HANDOFF`, `?FIX_LOOP`) that the vertical-tour gate treats as legitimate, so the note miscounts.
- [ ] (C) **`major`** signal, treating the default change as a breaking contract.
- [ ] (D) Other (describe).

**Recommended answer(s):** [(B)]

**Why:**

- `(B)` because the flip makes the miscount appear on *every capable scaffold* — it goes from a rare wart to the normal experience. It is a small fix and it makes the default-on output trustworthy. If you'd rather keep this change tight, (A) is fine and I'll file the count as a follow-up.
- `(C)` over-signals: `--no-icm` preserves the previous behaviour exactly, so nothing breaks that a user cannot restore with one flag. Save `major` for a change with no escape hatch.
- `(A)` is the minimal-correct answer; the only cost is that the very first output a new user sees counts three non-placeholders as placeholders.
